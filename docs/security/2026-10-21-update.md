# Security and operations update (2026-10-21)

This page summarizes the changes introduced by commits `4761f04` through `4cf64a8`. The production deployment on rabisuB was reported at `4cf64a8` on 2026-10-21. Host configuration and backup jobs are managed on the server; they are not reproduced by cloning this repository.

## Application changes

- API rate limits use Redis so workers share counters. The client key uses the trusted reverse proxy's `X-Real-IP` header; deployments must prevent untrusted clients from setting that header directly.
- SSO rejects an identity that is already bound to a different account. LDAP-derived JIDs include a digest of the directory DN to avoid name collisions.
- Uploads have a 120/hour rate limit, aggregate AI prompts have a 128 KiB character cap, and CSP metric directives are mapped to a fixed vocabulary.
- The local search index is isolated by account and cleared on logout.
- XMPP passwords are sealed in IndexedDB with a non-extractable AES-GCM browser key. Legacy plaintext session storage entries are migrated and removed. Same-origin JavaScript can still request decryption while the app is open, so this does not protect against XSS. A short-lived XMPP credential design remains future work.
- On a new OMEMO session, an unknown device is accepted with trust on first use; a changed known identity blocks sending until it is reviewed. Existing sessions do not recheck identity on every send. Legacy digest-only bundles are no longer treated as verified signatures, so old clients may need an upgrade and bundle republish.
- Decrypted message bodies are no longer persisted in the chat store's localStorage snapshot. Conversation metadata and drafts remain; opening a conversation reloads bodies from the encrypted local database.
- New WebSocket clients send the JWT in the `bearer.<token>` subprotocol alongside `liaot.v1`; the server selects `liaot.v1`. The query-string token remains available for older clients. Production nginx disables access logging for `/ws/`.
- `METRICS_TOKEN`, when configured, requires a bearer token for `/metrics`. Leaving it unset preserves the previous behavior, so the endpoint still needs network restrictions.

## Webhook credentials and delivery

Webhook authentication and signing use separate credentials. `POST /webhooks` returns the token and signing secret once. Save both securely; `GET /webhooks` does not return either. The preferred delivery endpoint is `POST /webhooks/{id}` with `Authorization: Bearer <token>`. The old `/webhooks/{id}/{token}` path remains available for existing integrations.

For a signed delivery, send `X-LyaoTalk-Timestamp` as Unix seconds and `X-LyaoTalk-Signature` as `sha256=<hex HMAC-SHA256>`. Sign the raw request body prefixed by the timestamp and a dot: `str(timestamp).encode() + b"." + raw_body`, using the signing secret. The timestamp must be within five minutes and may be used only once per webhook. `POST /webhooks/{id}/rotate-secret` issues a new signing secret and allows the old secret for 24 hours.

Unsigned deliveries remain accepted by default for compatibility and produce a warning. Set `WEBHOOK_SIGNATURES_REQUIRED=1` only after all senders sign requests. The replay guard currently accepts a correctly signed request if Redis is unavailable; operators who need strict replay rejection should change that failure behavior before enforcing signatures. Legacy URL tokens can appear in logs, so move integrations to the header endpoint.

## Server operations and verification

The rabisuB remediation report records corrected off-site and local backup contents, backup freshness alerts, release pruning, security headers, fail2ban, and Prosody configuration cleanup. Those host-level changes are not part of these Git commits. The release script now calls the server's release-pruning helper after a successful deployment.

The reported deployment passed the API health check, the unauthenticated 2 MiB upload rejection check, and live webhook authentication/signature cases. A local Windows verification of this branch passed the frontend build and all 109 frontend tests. These checks do not establish third-party OMEMO interoperability or an independently verified off-site restore.
